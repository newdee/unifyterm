| 问题 | 结论 |
|---|---|
| 个性还是共性 | 共性。"字段要么是它的类型，要么没给"这个假设，在读别的程序写的 JSON 的三处都有：agents 列表（`agents.rs`，9 个字段）、命令清单（`programs/read.rs`，29 个字段）、模型的回答（`assist/lib.rs`，8 个字段）。别处没有：更新检查读成 `Value` 再取字段；`ut mcp` 同样；自己的状态文件读不了就重写；设置和主题是 TOML，没有 `null` |

## 2026-11-23 · macOS 上长按字母键不重复输入

用户报告：Mac 上长按一个键不能连续输入。

- 原因：GPUI 的 `ElementInputHandler` 不改 `apple_press_and_hold_enabled`，默认值是 `true`。macOS 因此把长按的字母键交给重音菜单：`e` 弹出 é è ê，`k` 什么都不出。
- 定性：个性问题，只在 macOS 上出现；属于边界遗漏。全仓只有 `terminal.rs` 一处调用 `handle_input`，没有其他输入框。
- 改法：`TerminalInput` 包住 `ElementInputHandler`，其余方法原样转交，只让 `apple_press_and_hold_enabled` 返回 `false`。GPUI 只在 macOS 的按键代码里读这个值，Windows 和 Linux 不受影响。
- 代价：UnifyTerm 里长按不再弹重音菜单。iTerm2、WezTerm、kitty、Zed 的终端做法相同。输入法组字时仍先交给输入法，不受影响。

|---|---|---|---|
| 1 | 静态一致性 | `cargo clippy -p unifyterm --all-targets -D warnings`；搜 `handle_input` / `ElementInputHandler` | 0 警告；调用点 1 处 |
| 2 | 原行为不变 | Windows 上模拟长按 `a` 8 次（`WM_KEYDOWN` 第 30 位置 1） | PowerShell 收到 8 个 `a` |
| 3 | 回归 | `cargo test -p unifyterm` | 122 通过，0 失败，1 忽略 |

遗留：那台 Mac 离线（`link info` 3 秒无回答），macOS 的编译交给 CI，真实长按要用户确认。

- CI 三个平台通过（`9d2b7af`）。

### keepane 窗格里没有 UnifyTerm 的命令

## 2026-11-19 · 0.1.1：macOS 上从桌面启动的三个问题

用户第一次在 Mac 上手工打开 0.1.0，报告：`.zshrc` 第 66 行找不到 `/share/zsh-syntax-highlighting/…`，`zoxide` 和 `keepane` 找不到命令；追问后确认标签页开在 `/`。

### 定性

根因是同一个假设：**UnifyTerm 自己的启动环境（PATH、当前目录）就是用户的环境。** 从另一个 shell 里启动时成立；从访达、程序坞、开始菜单启动时不成立，而后者才是一个终端的常态（用户的原话："我们就是 term，为什么一定要从 shell 进"）。这是结构缺陷，不是边界遗漏。全仓找出这个假设的 4 处：

| # | 位置 | 表现 | 处理 |
|---|---|---|---|
| 1 | `shell.rs` 的 `command()`：zsh 不带 `-l` 启动 | macOS 上不读 `/etc/zprofile` 和 `~/.zprofile`，PATH 里没有 Homebrew。用户报告的就是这个 | 新增 `ShellStart`（`Login` / `Plain`）；macOS 用 `Login`：zsh 加 `-l` |
| 2 | 同上：bash、fish、PowerShell | 同样没有登录启动 | fish 加 `-l`，PowerShell 加 `-Login`（必须是第一个参数）；bash 带 `--rcfile` 时不能用 `-l`，由钩子读 `/etc/profile` 和 `~/.bash_profile`（或 `.bash_login`、`.profile`） |
| 3 | `session.rs` 的 `shell_command()`：标签页的目录取进程的当前目录 | 访达启动是 `/`；MSI 的开始菜单快捷方式是安装目录（`unifyterm.wxs` 写的 `WorkingDirectory="INSTALLFOLDER"`） | 标签页一律从主目录开始；`--cwd 目录` 指定别的。不再继承启动时的当前目录，也不去猜"这个目录是不是启动器留下的" |
| 4 | `agents.rs` 的 `run()`：用进程自己的 PATH 找 `keepane` | 访达启动时找不到，侧栏是空的 | 找不到时用登录 shell 找一次（`$SHELL -l -c 'command -v 名字'`），结果记住；只接受不含特殊字符的名字 |

第 3 条我先提的方案是"当前目录是 `/` 或程序所在目录时才改用主目录"。用户指出前提反了：不该把从 shell 启动当常态、把桌面启动当例外去识别。改成上表的规则后，那套判断整个不需要。

### 修改会不会引入新问题

| 风险 | 结论 |
|---|---|

### 已知限制

- 来自 uutils 内部的路径仍是 `\`：`ls -R` 的目录标题，`find -exec` 里的 `{}`。用户自己输入的 `\` 原样显示。

- uutils 的报错信息跟随系统语言（本机是中文）；`find` 在 Windows 上按系统格式输出，由 `ut` 转成 `/`；没有 `awk`、`rg`；`cmp` 说 "char" 而不是 "byte"；`cut -c` 按字节计。

### 已知限制

- 输入法的"组合中"状态（拼音候选窗、预编辑文字）没有自动化验证。已验证的是提交文本的通路（`WM_CHAR`，中文字符能进 shell）。
- 带 Ctrl、Shift、Alt 的组合键在检查里通过共享键盘状态发送，没有按真实键盘。
- 只在 Windows 11 上实测。macOS 和 Linux 的代码路径已写，未运行。
- release 构建在 32 并行任务下 rustc 两次崩溃（`STATUS_ACCESS_VIOLATION`，崩在不同 crate 上），`-j 6` 下 3 次都成功。
- Shift-Enter 发送换行符（Claude Code 里是换行）。PowerShell 里它不是"续行"，要等实现 win32-input-mode 或 kitty 键盘协议。
- release 构建在终端里打印时不阻塞 shell，文字会出现在下一个提示符之后。
